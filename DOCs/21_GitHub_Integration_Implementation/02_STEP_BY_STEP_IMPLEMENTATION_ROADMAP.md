## 1. Executive Implementation Overview

The GitHub Integration implementation is divided into **6 sequential, atomic phases**. Each phase is independently testable and produces tangible deliverables before moving to the next.

```text
Phase 1: Database Models & Prisma Migrations
   ↓
Phase 2: GitHub App Gateway & OAuth Authorization Service
   ↓
Phase 3: Repository Snapshot Ingestion & Ephemeral Workspace Manager
   ↓
Phase 4: Multi-Artifact AST & Config Parsers + Sanitizer
   ↓
Phase 5: Structured Project Context Engine & Flare Integration
   ↓
Phase 6: Frontend Context Panel & Repository Connection Experience
```

## 3. Detailed Phase Breakdown

### Phase 1: Database Models & Prisma Migrations

#### Objective
Define and migrate the relational models in Supabase PostgreSQL via Prisma to support GitHub App installations, connected repositories, scan histories, structured project contexts, and diagnostic evidence.

#### Tasks
1. Update `prisma/schema.prisma` with:
   - `GitHubConnection`
   - `Repository`
   - `RepositoryScan`
   - `ProjectContext`
   - `DiagnosticEvidence`
2. Generate and apply migration: `npx prisma migrate dev --name init_github_context`.
3. Verify models using Prisma Studio: `npx prisma studio`.

#### Definition of Done (DoD)
- [ ] Prisma migration runs cleanly without errors.
- [ ] TypeScript types generated by `@prisma/client` match `github-context.types.ts`.
- [ ] Database supports relational cascading deletes (e.g., disconnecting an account wipes associated scans/contexts).

---

### Phase 2: GitHub App Gateway & Authorization Service

#### Objective
Establish secure, server-side communication with GitHub App APIs. Handle App installation callbacks, CSRF validation, installation token generation, and repository listing.

#### Tasks
1. Create `backend/src/config/github.config.ts` with App ID, Private Key (PEM format), Client ID, Client Secret, and Webhook Secret.
2. Implement `github-auth.service.ts`:
   - Generate RS256 JWT for GitHub App authentication.
   - Request installation access tokens (`/app/installations/{id}/access_tokens`).
   - Store encrypted access tokens using AES-256-GCM.
3. Implement `github.controller.ts` with routes:
   - `GET /api/github/connect` (generates installation URL with signed state).
   - `GET /api/github/callback` (validates installation ID, syncs user connection).
   - `GET /api/github/repositories` (lists authorized repositories for the user).

#### Definition of Done (DoD)
- [ ] Server can authenticate as a GitHub App using private key JWT.
- [ ] Installation callback securely associates the GitHub account with the DeployFix user ID.
- [ ] Zero GitHub tokens or secrets are leaked to the client browser.

---

### Phase 3: Repository Snapshot Ingestion & Ephemeral Workspace

#### Objective
Stream and extract repository snapshots into an isolated, temporary scratch workspace with strict file limits and automated cleanup.

#### Tasks
1. Implement `workspace-manager.service.ts`:
   - Creates `/tmp/deployfix/scans/<scan_id>/`.
   - Limits: Maximum 50MB archive download, maximum 200MB uncompressed, maximum 5,000 files, maximum directory depth 10.
   - Automatic `try/finally` cleanup guaranteeing disk purge upon completion or failure.
2. Implement `github-client.service.ts`:
   - Streams tarball archive from GitHub API: `GET /repos/{owner}/{repo}/tarball/{ref}`.
   - Pipes stream through `tar.extract` into the ephemeral directory.
3. Implement `sanitization.service.ts`:
   - Rejects or deletes blacklisted files (`.env`, `*.pem`, `*.key`, `id_rsa`).
   - Enforces the **Zero Dynamic Code Execution Rule** (never runs scripts or binaries).

#### Definition of Done (DoD)
- [ ] Snapshot download and extraction completes in < 3 seconds for standard repositories (< 50MB).
- [ ] Ephemeral directory is completely erased from disk even if the extraction or parsing errors out.
- [ ] Zip-bombs and path traversal attempts (`../`) are detected and aborted immediately.

---

### Phase 4: Multi-Artifact AST & Config Parsers

#### Objective
Build dedicated, isolated parsers that extract exact architecture metadata from configuration files and manifests.

#### Tasks
1. `package-json.parser.ts`:
   - Parses dependencies, devDependencies, scripts, Node engine version.
   - Detects React, Vite, Next.js, Express, Fastify, NestJS, Prisma, TailwindCSS.
2. `dockerfile.parser.ts`:
   - Extracts base image (`FROM`), exposed ports (`EXPOSE`), build stages, and working directories.
3. `docker-compose.parser.ts`:
   - Maps service names, published/internal ports, service dependencies (`depends_on`), and environment files.
4. `nginx.parser.ts`:
   - Extracts listen ports, server names, `location` blocks, and `proxy_pass` targets.
5. `env-example.parser.ts`:
   - Parses key names without evaluating or storing values.
6. `prisma-schema.parser.ts`:
   - Detects datasource provider (`postgresql`, `mysql`, `sqlite`) and model definitions.
7. `workflow.parser.ts`:
   - Parses `.github/workflows/*.yml` for CI steps, node versions, and build commands.

#### Definition of Done (DoD)
- [ ] Unit test suite validates parsing across 20+ real-world sample repository configurations.
- [ ] Malformed or syntax-error files in repositories do not crash the engine; errors are logged as diagnostic notices.

---

### Phase 5: Structured Project Context Engine & Flare Integration

#### Objective
Synthesize all parsed artifacts into the standardized `ProjectContext` JSON, persist to PostgreSQL, and connect to the Flares Engine.

#### Tasks
1. Implement `project-context.service.ts`:
   - Merges parser outputs into the unified `ProjectContext` schema.
   - Calculates **Context Completeness Score** (adds +25% score for GitHub source).
   - Persists context record linked to `RepositoryScan`.
2. Connect to DeployFix Evidence & Flares Engine:
   - Evaluates Port Mismatch rules (e.g., Dockerfile `EXPOSE 5000` vs Nginx `proxy_pass http://localhost:3000`).
   - Evaluates Missing Environment Variable rules (`.env.example` keys vs active runtime env).
   - Generates evidence-backed Flares with root cause and suggested remediation.

#### Definition of Done (DoD)
- [ ] Complete Project Context JSON is saved to Supabase and queryable via `GET /api/github/repositories/:id/context`.
- [ ] Synthetic port mismatch and env mismatch test cases successfully trigger high-severity Flares.

---

### Phase 6: Frontend Context Panel & Connection Experience

#### Objective
Deliver a responsive, user-friendly interface for connecting GitHub, selecting repositories, viewing ingestion progress, and exploring detected context.

#### Tasks
1. Create `GitHubConnectCard.tsx` with clear state transitions:
   - `disconnected` -> `connecting` -> `connected` -> `ingesting` -> `error`.
2. Create `RepoSelectModal.tsx`:
   - Searchable repository dropdown, branch selector (`main`, `master`, custom), and 1-click "Analyze Repository" button.
3. Create `IngestedArtifactsGrid.tsx`:
   - Displays chips/badges for ingested artifacts (`✓ Dockerfile`, `✓ package.json`, `✓ nginx.conf`, `✓ CI Workflows`).
4. Create `FallbackSourceTabs.tsx`:
   - Public GitHub Repository URL input field for instant open-source scanning.
   - ZIP file drag-and-drop upload zone with client-side size verification.

#### Definition of Done (DoD)
- [ ] Full connection and repository selection flow works seamlessly in browser without console errors.
- [ ] UI provides real-time progress indicators and actionable error messages with retry buttons.
- [ ] Ingested context and Flares update the Dashboard instantly upon scan completion.
